## What We Did

### Stop lines → legend traces; removed checkboxes
- Rendered the **oracle stop** (green dashed) and **validation argmin** (purple dashed) lines as
  named scatter traces (`"oracle stop"`, `"val argmin"`) spanning the y-range, so they show up in
  the Plotly legend and toggle on/off by clicking the legend entry.
- **Removed all 8 checkboxes** (6 metric + 2 line). The 6 curves were already legend-clickable, so
  the checkboxes were redundant/messy. Everything is now toggled via legend clicks.

### Load-vs-run status messages
- `on_run` now peeks the cache index *before* the heavy work and sets an accurate message:
  - not cached → `running: computing N steps...`
  - fully cached → `loading from memory...`
  - partially cached → `loading from memory, then running +Δ steps...`
- Caveat noted to the user: Jupyter may not repaint the label mid-callback (kernel busy), so the
  two-phase message may not always render; a background thread would be the reliable fix if wanted.
- Explained the "loading is slow" question: on a pure load the compute is skipped; the cost is
  pickle-loading the stored data matrices + full-length trajectories and Plotly rendering every step
  (large for long runs). Offered display-downsampling as a future option (not yet implemented).

### Cache-deletion incident + new safety rule
- Discovered my own test cleanup (`rm -f logistic_cache/*.pkl index.json`) had been deleting the
  user's real cache, since it targeted the same live directory the notebook writes to.
- Added a **"Be Careful When Deleting or Testing"** section to `CLAUDE.md`: never erase user
  data/caches, always use a throwaway temp dir for test artifacts, confirm before deleting.
- Going forward, verification runs use an isolated `/tmp` cache dir.

### Highest-T behavior confirmed
- Verified (in an isolated temp cache) that the setup-keyed cache keeps exactly **one record per
  setup at the highest T** ever run: T=20 → computed, T=50 → extended, T=30 → cache-hit (returns 30
  for display but does not shrink the stored record). Ends with 1 index entry, steps=50. No code
  change needed — already the intended behavior.
