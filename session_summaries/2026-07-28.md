## New notebook: `wtilde_average_convergence.ipynb`

Built a new assistant-owned visualization answering the question:
**does the average of many `w̃` draws converge to `w*` (and `L(w̄) → L(w*)`)?**

- Generator: `ali_code/LLM_visualization/build_wtilde_average_convergence_notebook.py`
  → emits `ali_code/LLM_visualization/wtilde_average_convergence.ipynb`
  (same pattern as `region_visualization`: rebuild-module cell, cache, control
  panel, legend-toggle Plotly figure).

### What it does
- Each `w̃ = find_w_tilde(X, y)` is treated as **one draw from a random distribution**;
  the randomness is a fresh `(X, y)` from `generate_data` (no training set — every
  draw is independent, drawn from the seeded class RNG).
- Accumulates the running mean `w̄_N = (1/N) Σ w̃_n` and, for each `N` (x-axis =
  number of draws), records:
  - `‖w̄_N − w*‖` (norm difference)
  - `angle(w̄_N, w*)` in degrees (scale-invariant — the meaningful signal for raw `w̃`)
  - `L(w̄_N)` — population logistic loss on a **fresh, large held-out sample**
    (`test_size`, drawn from a separate RNG so it doesn't perturb the draw sequence)
  - `L(w*)` — constant dashed reference line
- **Toggles requested by Ali:**
  - `w̃` is the **unnormalized** max-margin solution by default (do NOT normalize).
  - `normalize_w_tilde` checkbox normalizes *each* `w̃` to unit norm before
    averaging, to focus purely on direction.
- Control panel exposes `n, d, k, N draws, eta, seed, test_size, normalize_w_tilde`,
  plus `log x` / `log y` axis toggles, a Run/load button, and a saved-runs dropdown.
- Run cache: `wtilde_avg_cache/` (one entry per setting; identity ignores `N_draws`
  so a larger `N` extends the entry, smaller/equal reloads + truncates).

### Verified
- Headless smoke test (d=40, n=30, k=4, N=20): `L(w̄)=0.594` vs `L(w*)=0.575`,
  angle ~60° and shrinking. Confirmed the expected caveat: with raw `w̃`,
  `‖w̄‖ ≫ ‖w*‖` (≈4.8 vs 2.0), so **norm-diff does not go to 0** — angle is the
  convergence signal for the unnormalized case.
- `import numpy, cvxpy` ~2s, so slow VS Code kernel *restart/connect* is an
  environment/VS Code-extension issue, not the notebook or the venv imports.
