## Key design (discussed at length before coding)
- **Store per-axis dot products, not full trajectories.** For each iterate store
  `P[i,t,a] = ⟨w_{i,t}, v_a⟩` against unit candidate axes `v_a`, plus the axis Gram matrix
  `G[a,b] = ⟨v_a, v_b⟩`. This is ~200× smaller than the d-dim trajectory (`T×n_axes` vs `T×d`).
- **View-time reconstruction.** Any chosen axis pair `(a=x, b=y)` is turned into an orthonormal
  2D frame at draw time via Gram–Schmidt on `G`:
  `x = P[·,a]/√G[a,a]`, `y = (P[·,b] − (G[a,b]/G[a,a])P[·,a]) / √(G[b,b] − G[a,b]²/G[a,a])`.
  Derived/checked together (incl. the `√(1 − cos²)` denominator, which must stay even for unit axes).
- **Magnitude is preserved.** Axes are unit-normalized *for projection only*; the raw `w*` and
  `w̃_i` are returned separately at true magnitude so markers land at real scale
  (`w*` at `(‖w*‖, 0)` when x-axis = `w*`). Verified.
- **Anchor asymmetry** is inherent: whichever vector is chosen for x sits exactly on +x; the
  y-pick is orthogonalized (`v₂^⊥`) and tilts by its correlation with x.

## Planned next — over-time trajectory comparison (a NEW plot type, not a projection)
Ali wants a new mode that is deliberately different from v1–v3: **x-axis = time (GD step)**, not a
2D spatial projection. Proposed name: **`LLM_generated_trajectory_comparison_over_time`**
(distinct name on purpose — it is not "v4" of the projection family).

For a **pair** of trajectories `w¹_t`, `w²_t` (selectable which two), plot vs. `t`:
1. **`angle(w¹_t, w²_t)`** — the angle between the two weight vectors at each step.
2. **`‖w¹_t − w²_t‖`** — the norm of their difference, restricted to a **selectable coordinate
   subset**: the first `k` coordinates, the last `d−k` coordinates, or all `d`. The split point
   `k` should be selectable (default = the model's signal dimension `k`, i.e. `w*`'s support).

Key point: these metrics are computed from the **full weight vectors over time**, so this mode
does **not** use v3's `P`/`G` projection machinery at all — it needs the actual `w_t` values (or
metrics derived from them), not 2D projections.

**Open design question to settle first (storage):** how to allow an *arbitrary* view-time `k`
without pickling the full `T×d` trajectories (which is exactly what we avoided in v3). Options to
weigh next session:
  - store only a few **preset** coordinate-split series (first-k / last-(d−k) / all) → cheap
    (`~3×T`) but `k` is fixed at run time, not browsable;
  - store the **cumulative-over-coordinates** squared-difference `C[t, m] = Σ_{j<m}(w¹_t−w²_t)²_j`
    so any split `k` is `√C[t,k]` / `√(C[t,d]−C[t,k])` at view time — but `C` is `T×d` (no smaller
    than the trajectory);
  - **time-subsample** (log-spaced steps, since `‖w_t‖ ~ log t`) to shrink `T`, then either of
    the above becomes affordable.
`angle(w¹_t, w²_t)` is a single `(T,)` series and is cheap regardless.
